06 - Servicios e Inyección de Dependencias

Los servicios y la inyección de dependencias (DI) son la columna vertebral de cualquier aplicación Angular real. Un servicio encapsula lógica reutilizable, estado compartido y acceso a datos, mientras que DI se encarga de proporcionar esos servicios a los componentes que los necesitan de forma declarativa y desacoplada.

En este módulo avanzado profundizaremos en patrones como factory providers, InjectionToken, multi providers e inyectores jerárquicos para dominar completamente el sistema de DI de Angular 17+.

Conceptos clave

  • @Injectable - Decorador que marca una clase como servicio disponible para DI
  • providedIn - Opción de @Injectable que define el alcance del proveedor ('root', 'platform', 'any')
  • Injector - Clase que gestiona la resolución e instanciación de dependencias
  • inject() - Función de utilidad para inyectar dependencias fuera de constructores (Angular 14+)
  • Singleton pattern - Patrón donde una única instancia de servicio comparte estado globalmente
  • providers array - Arreglo en la configuración de módulos/componentes que registra proveedores
  • useValue - Estrategia de proveedor que inyecta un valor estático
  • useFactory - Estrategia de proveedor que usa una función para crear la instancia
  • useExisting - Estrategia de proveedor que referencia otro proveedor ya registrado
  • InjectionToken - Token tipado para inyectar valores que no son clases (configuraciones, constantes)
  • Hierarchical injectors - Sistema de resolución de DI que sube la jerarquía de árbol de componentes
  • providedIn: 'root' - Hace que un servicio esté disponible globalmente como singleton sin declararlo en providers
01Servicio básico con @Injectable ⭐
Objetivo
Crear un servicio usando el decorador @Injectable y registrarlo en la aplicación.
Enunciado
Crea un servicio llamado FechaService que exponga métodos para obtener la fecha actual, formatear una fecha como cadena de texto y calcular la diferencia en días entre dos fechas. El servicio debe usar providedIn: 'root' para estar disponible globalmente sin necesidad de declararlo explícitamente en ningún módulo.
Requisitos
  • El servicio debe tener el decorador @Injectable({ providedIn: 'root' })
  • Método obtenerFechaActual() que retorne un objeto Date
  • Método formatearFecha(fecha: Date): string que retorne la fecha en formato DD/MM/AAAA
  • Método diferenciaEnDias(f1: Date, f2: Date): number que retorne la diferencia absoluta en días
  • Inyectar el servicio en un componente y mostrar los resultados en la plantilla
El método providedIn: 'root' en el decorador @Injectable registra el servicio en el inyector raíz automáticamente, sin necesidad de agregarlo al array providers de ningún módulo.
02Inyección de servicios en componentes ⭐⭐
Objetivo
Dominar las diferentes formas de inyectar un servicio en un componente.
Enunciado
Crea un servicio CalculadoraService con métodos para sumar, restar, multiplicar y dividir dos números. Luego crea un componente CalculadoraComponent que permita al usuario elegir dos números y una operación, y muestre el resultado. Implementa la inyección de las dos formas soportadas por Angular 17+.
Requisitos
  • Crear el servicio CalculadoraService con providedIn: 'root'
  • Métodos: sumar(a, b), restar(a, b), multiplicar(a, b), dividir(a, b)
  • Implementar la inyección vía constructor (forma clásica)
  • Crear un segundo componente que use inject(CalculadoraService) (forma moderna)
  • Ambos componentes deben funcionar correctamente y mostrar los resultados
  • Manejar el caso de división por cero con un mensaje de error
En Angular 17+ puedes usar private calcService = inject(CalculadoraService) directamente como propiedad de la clase sin necesidad de declarar el parámetro en el constructor.
03Servicios singleton: demostrando estado compartido ⭐⭐
Objetivo
Demostrar que un servicio registrado en el inyector raíz funciona como singleton, compartiendo su estado entre múltiples componentes.
Enunciado
Crea un servicio ContadorService que mantenga un número entero en su estado interno con métodos para incrementar, decrementar y obtener el valor actual. Luego crea dos componentes diferentes (PanelAComponent y PanelBComponent) que inyecten el mismo servicio. Demuestra que al modificar el contador en un panel, el otro panel refleja el cambio inmediatamente.
Requisitos
  • Servicio con propiedad privada private contador: number = 0
  • Métodos: incrementar(), decrementar(), obtenerValor(): number
  • Ambos componentes deben inyectar el mismo servicio
  • Mostrar el valor actual del contador en ambos componentes simultáneamente
  • Crear un componente padre que incluya ambos paneles y compruebe el valor final
Debido a que providedIn: 'root' registra el servicio en el inyector raíz, Angular crea una sola instancia que se comparte entre todos los componentes que lo inyecten.
04Patrón de servicio Logger ⭐⭐
Objetivo
Implementar un servicio de logging como patrón de diseño transversal para toda la aplicación.
Enunciado
Crea un servicio LoggerService que permita registrar mensajes con diferentes niveles de severidad (info, warning, error). El servicio debe almacenar un historial de mensajes y ofrecer métodos para consultarlos. Crea al menos tres componentes que usen el logger para registrar eventos, demostrando que el historial se comparte.
Requisitos
  • Definir una interfaz LogEntry con campos: mensaje, nivel, timestamp
  • Métodos: info(msg), warn(msg), error(msg)
  • Método obtenerHistorial(): LogEntry[] que retorne todos los registros
  • Método limpiarHistorial() que vacíe el array de logs
  • Tres componentes distintos que inyecten y usen el servicio
  • Un componente LogViewerComponent que muestre el historial completo
El servicio Logger es un patrón transversal: se inyecta en múltiples puntos de la aplicación y su estado (el array de historial) se comparte porque es singleton.
05Servicio Counter compartido entre componentes ⭐⭐⭐
Objetivo
Crear un servicio que gestione un contador con eventos reactivos usando RxJS, compartido entre componentes hermanos.
Enunciado
Crea un servicio SharedCounterService que gestione un contador utilizando BehaviorSubject. Crea dos componentes hermanos: IncrementadorComponent (con botones de +1 y -1) y DisplayCounterComponent (que solo muestra el valor). Ambos se comunican exclusivamente a través del servicio.
Requisitos
  • Usar BehaviorSubject<number> con valor inicial de 0
  • Exponer un Observable<number> público mediante asObservable()
  • Métodos: incrementar(), decrementar(), reset()
  • IncrementadorComponent con botones para cada operación
  • DisplayCounterComponent que se suscriba al observable y muestre el valor
  • Crear un componente padre que contenga ambos componentes hermanos
Usa BehaviorSubject en lugar de Subject porque emite el valor actual a nuevos suscriptores inmediatamente. Exponlo con asObservable() para evitar que otros componentes llamen a next() directamente.
06Servicio con estado privado y métodos públicos ⭐⭐⭐
Objetivo
Diseñar un servicio que encapsule completamente su estado interno y solo exponga una API pública controlada, aplicando principios de encapsulamiento.
Enunciado
Crea un servicio TareasService que gestione una lista de tareas (todo list). El servicio debe tener toda su estado como propiedades privadas y exponer únicamente métodos públicos para interactuar con las tareas. Implementa operaciones CRUD completas con validación interna.
Requisitos
  • Definir interfaz Tarea con campos: id, titulo, completada, fechaCreacion
  • Estado interno privado: private tareas: Tarea[] = [] y private nextId = 1
  • Métodos públicos: agregar(titulo), eliminar(id), alternarCompletada(id), obtenerTodas(), obtenerPendientes()
  • El método agregar debe validar que el título no esté vacío
  • El método eliminar debe manejar el caso de que el id no exista
  • Un componente que consuma el servicio y muestre la lista de tareas con botones de acción
Nunca expongas el array interno directamente con obtenerTodas() retornando la referencia. Retorna una copia con [...this.tareas] o usa readonly para evitar modificaciones externas no controladas.
07Factory providers y useFactory ⭐⭐⭐⭐
Objetivo
Comprender y aplicar la estrategia de proveedores useFactory para crear instancias de servicios con lógica condicional o configuración dinámica.
Enunciado
Crea dos servicios: ConsolaLoggerService y AlertaLoggerService, ambos con la misma interfaz pero implementaciones diferentes. Luego crea un factory function que decida cuál de los dos servicios instanciar según una condición de entorno (por ejemplo, una variable booleana esProduccion). Registra el factory provider en la configuración del componente.
Requisitos
  • Crear interfaz LogStrategy con método registrar(mensaje: string): void
  • ConsolaLoggerService que implemente la interfaz y use console.log
  • AlertaLoggerService que implemente la interfaz y use window.alert o muestre un toast
  • Factory function que retorne la instancia correcta según la condición
  • Registrar el provider usando useFactory en el array providers del componente
  • Un componente que consuma el servicio inyectado y pruebe ambos modos
El useFactory recibe una función que retorna la instancia del servicio. Puedes pasar dependencias adicionales usando el tercer argumento del objeto provider con deps: [OtherService].
08InjectionToken para valores personalizados ⭐⭐⭐⭐
Objetivo
Usar InjectionToken para inyectar valores que no son instancias de clases, como configuraciones, constantes o datos de entorno.
Enunciado
Crea una configuración de aplicación usando InjectionToken. Define tokens para la URL base de la API, el timeout de peticiones y el modo debug. Luego crea un servicio ApiService que consuma estos valores inyectados y un componente que muestre la configuración actual.
Requisitos
  • Crear InjectionToken<string> llamado API_URL
  • Crear InjectionToken<number> llamado REQUEST_TIMEOUT
  • Crear InjectionToken<boolean> llamado DEBUG_MODE
  • Registrar los tokens con useValue en el providers del componente o módulo
  • Servicio ApiService que inyecte los tres tokens y exponga un método obtenerConfiguracion()
  • Componente que muestre los valores de configuración inyectados
  • Crear una interfaz ApiConfig que agrupe todos los valores y un token único API_CONFIG
InjectionToken es preferible a OpaqueToken (ya obsoleto) porque permite definir un tipo genérico. Cuando uses useValue, el valor se inyecta tal cual sin instanciación.
09Multi providers ⭐⭐⭐⭐
Objetivo
Dominar la estrategia multi: true para registrar múltiples proveedores bajo un mismo token y consumirlos como un array.
Enunciado
Crea un sistema de validadores de formulario usando multi providers. Define un InjectionToken llamado VALIDADORES y registra múltiples funciones validadoras (longitud mínima, solo números, email válido) como multi providers. Un servicio ValidadorService debe inyectar el array de validadores y aplicar todos ellos a un valor de entrada.
Requisitos
  • Crear tipo ValidatorFn como (valor: string) => boolean
  • Crear InjectionToken<ValidatorFn[]> llamado VALIDADORES
  • Registrar al menos 3 validadores con multi: true y useValue
  • Servicio ValidadorService que inyecte el array y ejecute todos los validadores
  • Método validar(valor: string): { valido: boolean; errores: string[] }
  • Componente con un campo de texto y botón que valide el valor contra todos los validadores
  • Mostrar los errores de validación en pantalla
Cuando usas multi: true, Angular agrega tu proveedor al array existente del token en lugar de reemplazarlo. Esto permite que múltiples módulos o componentes contribuyan proveedores al mismo token.
10Inyectores jerárquicos: nivel componente vs nivel app ⭐⭐⭐⭐⭐
Objetivo
Comprender y demostrar cómo funciona la jerarquía de inyectores en Angular: un servicio registrado en un componente tiene una instancia diferente al registrado en la raíz.
Enunciado
Crea un servicio AnimalService que genere un ID único por instancia (un contador que se incrementa en el constructor). Registra una instancia global con providedIn: 'root' y otra instancia a nivel de componente específico con providers: [AnimalService]. Demuestra que los IDs son diferentes, probando también con providers: [] vacío para ver la resolución jerárquica.
Requisitos
  • Servicio AnimalService con una propiedad instanciaId asignada en el constructor
  • Usar una propiedad estática static contador = 0 para generar IDs únicos
  • Componente RootAnimalComponent que inyecte el servicio global (sin providers extras)
  • Componente EspecialAnimalComponent con providers: [AnimalService] que cree una nueva instancia
  • Componente padre que muestre ambos IDs y compruebe que son diferentes
  • Demostrar que al agregar providers: [AnimalService] a un componente nieto, hereda la instancia del padre, no la global
  • Crear un tercer nivel de jerarquía para demostrar la resolución ascendente
Cuando declaras providers: [AnimalService] en un componente, Angular crea una nueva instancia para ese componente y todos sus hijos. Los componentes fuera de esa rama siguen usando la instancia global. La resolución sube por la jerarquía hasta encontrar un proveedor.
11Clases abstractas como interfaces de servicio ⭐⭐⭐⭐⭐
Objetivo
Usar clases abstractas como contratos de servicios para lograr desacoplamiento total y permitir intercambio de implementaciones sin modificar los componentes consumidores.
Enunciado
Crea un sistema de persistencia de datos donde la interfaz es una clase abstracta BasePersistenciaService y existen dos implementaciones concretas: LocalStorageService y MemoriaService. Un componente DatosComponent debe inyectar la clase abstracta y funcionar correctamente con cualquiera de las dos implementaciones, intercambiadas a través de providers.
Requisitos
  • Clase abstracta BasePersistenciaService con métodos abstractos: guardar(clave, valor), obtener(clave), eliminar(clave), obtenerTodasLasClaves()
  • LocalStorageService que implemente usando localStorage del navegador
  • MemoriaService que implemente usando un Map<string, any> en memoria
  • Ambas clases deben extender la abstracta y usar @Injectable() sin providedIn
  • Componente que inyecte BasePersistenciaService (la abstracta)
  • Registrar la implementación concreta usando useExisting o useClass en los providers
  • Demostrar que al cambiar el provider, el componente funciona con la otra implementación sin modificaciones
Las clases abstractas en TypeScript son ideales como contratos de DI porque permiten definir tipos sin implementación. Usa { provide: BasePersistenciaService, useClass: MemoriaService } para mapear la abstracta a la concreta.
12Aplicación completa: servicio de configuración multi-componente ⭐⭐⭐⭐⭐
Objetivo
Integrar todos los conceptos de servicios y DI en una aplicación completa que use un servicio de configuración compartido entre múltiples componentes.
Enunciado
Crea una aplicación de gestión de apariencia (theme). Un servicio ConfiguracionService gestionará el tema (claro/oscuro), el tamaño de fuente y el idioma. Múltiples componentes consumirán y modificarán esta configuración: un panel de control para cambiar opciones, un header que reaccione al tema, un contenido que cambie el tamaño de texto y un footer que muestre el idioma actual.
Requisitos
  • Crear InjectionToken para la configuración inicial con valores por defecto
  • Servicio ConfiguracionService con BehaviorSubject para cada opción
  • Propiedades reactivas: tema$, tamanioFuente$, idioma$
  • Métodos: cambiarTema(tema), cambiarTamanoFuente(size), cambiarIdioma(lang)
  • Método obtenerConfiguracionCompleta() que retorne un objeto con todas las opciones
  • Componente PanelControlComponent con controles para cada opción
  • Componente HeaderComponent que cambie estilos según el tema
  • Componente ContenidoComponent que ajuste el tamaño de fuente
  • Componente FooterComponent que muestre el idioma activo
  • Un LoggerService que registre cada cambio de configuración con timestamp
  • Todos los componentes deben reaccionar a los cambios en tiempo real usando async pipe o suscripciones
  • Aplicar al menos un useFactory para inicializar la configuración según el entorno
Combina InjectionToken con useValue para los valores iniciales, BehaviorSubject para el estado reactivo, y asegúrate de inyectar el LoggerService también en el ConfiguracionService para registrar los cambios. El async pipe simplifica la suscripción en plantillas.
