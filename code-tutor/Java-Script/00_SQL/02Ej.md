# Exercise 02: SELECT with WHERE Conditions

## Reference: `db.prepare()` and `.all()`

In this codebase, `db.prepare()` and `.all()` come from **better-sqlite3** (a synchronous SQLite library for Node.js).

**`db.prepare(sql)`** — compiles a SQL string into a reusable prepared statement object. It protects against SQL injection by treating `?` placeholders as bound parameters.

**`.all(...params)`** — executes the prepared statement and returns **all** matching rows as an array of JavaScript objects (one per row, column names as keys).

```js
// Two-step (reusable):
const stmt = db.prepare('SELECT * FROM users WHERE age > ?');
const adults = stmt.all(18);

// One-step (inline):
const users = db.prepare('SELECT * FROM users').all();

// Result: [{ id: 1, name: 'Alice', ... }, { id: 2, name: 'Bob', ... }]
```

Sibling methods on a prepared statement:
- **`.get(...)`** — returns a single row (or `undefined`)
- **`.run(...)`** — executes INSERT/UPDATE/DELETE, returns `{ changes, lastInsertRowid }`

Key difference from `.get()`: `.all()` always returns an array (possibly empty); `.get()` returns one object or `undefined`.

## Clarification: `prepare()` as a Template/Mold

You're on the right track, but let me refine it a bit:

**`db.prepare(sql)`** is more like a **template/mold** than just an envelope. It pre-compiles the SQL so SQLite doesn't have to re-parse it every time, and it locks in the `?` placeholders for safe parameter binding. You create it once, then call `.all()`, `.get()`, or `.run()` on it multiple times with different values.

```js
const stmt = db.prepare('SELECT * FROM products WHERE category = ?');
//   ^^^ compiled once, reusable

stmt.all('electronics');  // same template, different value
stmt.all('clothing');     // same template, different value
```

**`.all()`** is one of the execution methods on that prepared statement — it specifically means "give me **every** matching row as an array."

So it's not wrong to call it a "layer" — `better-sqlite3` is indeed the JS↔SQLite bridge — but `db.prepare()` is specifically the **preparation step**, and `.all()` is the **"give me everything"** execution mode.

## Debugging: Duplicate `const` Declaration

A common mistake is accidentally declaring the same `const` variable twice in the same scope. `const` cannot be reassigned or redeclared — doing so throws a `SyntaxError` and the script won't run at all.

Here's the problematic code:

```js
const olderUsers = db.prepare('SELECT * FROM users WHERE age > ?').all(25);
const olderUsers = []; // ❌ SyntaxError: Identifier 'olderUsers' has already been declared
console.table(olderUsers);
```

**Fix:** Remove the unused declaration — keep only the real query:

```js
const olderUsers = db.prepare('SELECT * FROM users WHERE age > ?').all(25);
console.table(olderUsers);
```

**Lesson:** When using `const`, you can only declare a variable **once** per scope. If you see `SyntaxError: Identifier has already been declared`, look for duplicate `const` (or `let`) with the same name.

## Debugging: Gmail Email Filter

This is a record of the mistakes encountered while implementing Task 2 (retrieve users with `@gmail.com` emails) and the fixes applied.

### Original buggy code

```js
const statementMail = db.prepare('SELECT * FROM users WHERE email like "%@gmailUsers.com"');
const gmailUsers = statementMail;
console.table(gmailUsers);
```

### Mistakes found

| # | Mistake | Fix |
|---|---------|-----|
| 1 | **Wrong domain in pattern**: `%@gmailUsers.com` — no users have this domain in the seed data | Changed to `%@gmail.com` |
| 2 | **SQL string literal used double quotes**: `"%@gmail.com"` — SQLite interprets double quotes as column identifiers, not string values | Changed to single quotes inside the SQL: `'%@gmail.com'` |
| 3 | **Statement never executed**: `gmailUsers = statementMail` assigns the prepared statement object itself, not the query results | Changed to `statementMail.all()` to execute and return rows |
| 4 | **Unicode characters invisible**: `console.table()` draws box-drawing characters (┌─┐) that don't render in some Windows terminals | Changed to `console.log()` for plain-text output |

### Final corrected code

```js
const statementMail = db.prepare("SELECT * FROM users WHERE email LIKE '%@gmail.com'");
const gmailUsers = statementMail.all();
console.log(gmailUsers);
```

### Verified output

```
[
  { id: 3, name: 'Charlie', email: 'charlie@gmail.com', age: 35 },
  { id: 6, name: 'Frank', email: 'frank@gmail.com', age: 40 }
]
```

### Minor observation (not a bug)

The task says *"Retrieve the **name and email**"* but the query uses `SELECT *` which returns all columns (`id`, `name`, `email`, `age`). Could be narrowed to `SELECT name, email` for precision, but functionally correct.

## Debugging: Products Between $20 and $100

This is a record of the mistakes encountered while implementing Task 3 (retrieve products priced between 20 and 100) and the fixes applied.

### Original buggy code

```js
const precioMas = db.prepare('SELECT * FROM products WHERE price between $20 AND $100');
const midRangeProducts = precioMas.all();
console.log(midRangeProducts);
```

### Mistakes found

| # | Mistake | Fix |
|---|---------|-----|
| 1 | **`$20` and `$100` used as literals**: In SQLite, `$` prefix creates a **named parameter** (like a `?` placeholder), not a numeric value. SQLite looks for a bound value that was never provided | Remove the `$` signs — use plain numbers: `BETWEEN 20 AND 100` |
| 2 | **`BETWEEN` syntax correct**: `BETWEEN` and `AND` are used properly — no fix needed for this part | ✅ Already correct |

### Key concept: `$` in SQLite

In SQLite (and better-sqlite3), `$name`, `@name`, and `:name` are **named parameter placeholders**, just like `?` is a positional placeholder. They are **not** variable interpolation in SQL.

```js
// ❌ Wrong — $20 is a named parameter, not the number 20
db.prepare('SELECT * FROM products WHERE price BETWEEN $20 AND $100');

// ✅ Correct — raw numbers in SQL
db.prepare('SELECT * FROM products WHERE price BETWEEN 20 AND 100');

// ✅ Also correct — named parameters with bound values
const stmt = db.prepare('SELECT * FROM products WHERE price BETWEEN $min AND $max');
stmt.all({ min: 20, max: 100 });
```

### Final corrected code

```js
const precioMas = db.prepare('SELECT * FROM products WHERE price BETWEEN 20 AND 100');
const midRangeProducts = precioMas.all();
console.log(midRangeProducts);
```

### Verified output

```
[
  { id: 3, name: 'Shirt', price: 30, stock: 100, category: 'clothing' },
  { id: 4, name: 'Jeans', price: 60, stock: 50, category: 'clothing' },
  { id: 7, name: 'JavaScript Book', price: 45, stock: 30, category: 'books' },
  { id: 8, name: 'SQL Guide', price: 35, stock: 20, category: 'books' }
]
```

## Debugging: Wildcard Product Search

This is a record of the mistakes encountered while implementing Task 4 (find products containing 'book' or 'guide' in their names) and the fixes applied.

### Original buggy code

```js
const bookOrGuideProducts = db.prepare('SELECT * FROM products WHERE name LIKE '%book%' OR '%guide%' ').run();
console.log(bookOrGuideProducts);
```

### Mistakes found

| # | Mistake | Fix |
|---|---------|-----|
| 1 | **Single-quote JS string clashes with single-quote SQL literals**: `'...LIKE '%book%'...'` -- the `'` before `%book%` closes the JS string early, making `book` a JS variable -> `ReferenceError: book is not defined` | Use double quotes for the JS string: `"SELECT ... LIKE '%book%'"` |
| 2 | **Missing `name LIKE` before second condition**: `OR '%guide%'` is incomplete -- it's just a string literal, not a comparison | Add `name LIKE` before `'%guide%'`: `OR name LIKE '%guide%'` |
| 3 | **`.run()` used for SELECT**: `.run()` is for INSERT/UPDATE/DELETE and returns `{ changes, lastInsertRowid }`, not rows | Use `.all()` to get matching rows as an array |

### Key concept: Escaping quotes in SQL + JS

When embedding SQL with string literals inside a JavaScript string, you must avoid quote conflicts:

```js
// Wrong -- single quotes clash
db.prepare('SELECT * FROM products WHERE name LIKE '%book%'');

// Fix 1: Use double quotes for JS string
db.prepare("SELECT * FROM products WHERE name LIKE '%book%'");

// Fix 2: Escape the inner single quotes
db.prepare('SELECT * FROM products WHERE name LIKE \'%book%\'');
```

### Final corrected code

```js
const bookOrGuideProducts = db.prepare("SELECT * FROM products WHERE name LIKE '%book%' OR name LIKE '%guide%'").all();
console.log(bookOrGuideProducts);
```

### Verified output

```
[
  { id: 7, name: 'JavaScript Book', price: 45, stock: 30, category: 'books' },
  { id: 8, name: 'SQL Guide', price: 35, stock: 20, category: 'books' }
]
```


## Debugging: Logical Combinations

This is a record of the mistakes encountered while implementing Task 5 (products that are EITHER electronics OR price < 50, AND have stock > 0) and the fixes applied.

### Original buggy code

```js
const conditionalProducts = db.prepare("SELECT * FROM products WHERE category = 'electronics' OR price < 50 AND stock > 0");
console.log(conditionalProducts);
```

### Mistakes found

| # | Mistake | Fix |
|---|---------|-----|
| 1 | **Statement not executed**: `conditionalProducts` is the prepared statement object, not the query result. `console.log` prints Statement metadata instead of rows | Add `.all()` after `db.prepare(...)` to execute the query |
| 2 | **Missing parentheses for OR/AND precedence**: In SQL, `AND` binds tighter than `OR`. `... OR price < 50 AND stock > 0` is parsed as `... OR (price < 50 AND stock > 0)`, which lets electronics with 0 stock through (like Mouse) | Wrap the OR condition in parentheses: `(category = 'electronics' OR price < 50) AND stock > 0` |

### Key concept: SQL operator precedence

In SQLite, `AND` has higher precedence than `OR` (like `*` before `+` in math). Without parentheses:

```sql
-- Parsed as: category = 'electronics' OR (price < 50 AND stock > 0)
-- NOT:       (category = 'electronics' OR price < 50) AND stock > 0
SELECT * FROM products WHERE category = 'electronics' OR price < 50 AND stock > 0;
```

### Final corrected code

```js
const conditionalProducts = db.prepare("SELECT * FROM products WHERE (category = 'electronics' OR price < 50) AND stock > 0").all();
console.log(conditionalProducts);
```

## 🛠️ Setting Up SQLite CLI — Running SQL Directly in the Terminal

To write SQL commands directly in the terminal (without Node.js), you need the **SQLite Command-Line Shell (`sqlite3.exe`)**. Once installed, you open a database with `sqlite3 ex02.db` and type raw SQL interactively.

> **Status check:** `sqlite3` was **not found** on this system — it needs to be installed.

### 1. Download SQLite
1. Go to the official SQLite download page: [https://www.sqlite.org/download.html](https://www.sqlite.org/download.html)
2. Scroll down to **Precompiled Binaries for Windows**.
3. Download **`sqlite-tools-win-x64-*.zip`** (or `win32` for older 32-bit systems).

### 2. Where to Put It
Extract the `.zip` into a **dedicated folder** — not your project folder — so it's accessible from any project:

```
C:\sqlite\
  sqlite3.exe   <- the CLI tool
  sqldiff.exe
  sqlite3_analyzer.exe
```

> **Advice:** Avoid placing `sqlite3.exe` directly inside your project folder. Using `C:\sqlite` keeps it global and reusable.

### 3. Add `C:\sqlite` to Your System PATH
This makes the `sqlite3` command work in any terminal window:

1. Press **Windows Key**, search **"Environment Variables"**, select **"Edit the system environment variables"**.
2. Click **"Environment Variables..."**.
3. Under **System variables**, select **`Path`** and click **Edit**.
4. Click **New** and type `C:\sqlite`.
5. Click **OK** on all windows to save.

### 4. How to Use It

Restart your terminal (or VS Code) so it picks up the new PATH. Then:

```bash
sqlite3 ex02.db
```

You'll see the interactive prompt:

```
SQLite version 3.x.x
Enter ".help" for usage hints.
sqlite>
```

Now type SQL directly:

```sql
SELECT * FROM users WHERE age > 25;
SELECT name, email FROM users WHERE email LIKE '%@gmail.com';
.tables        -- list all tables
.schema users  -- show table structure
.quit          -- exit
```

> Don't forget the **semicolon `;`** at the end of every SQL statement!
